## 背景

`platform-api` 是身份、IAM、用户、项目、服务账号和审计的控制面权威，`platform-web` 是唯一正式 UI 消费端。当前实现已经分离平台角色与项目角色，但仍存在以下问题：信任客户端租户上下文；用户管理权限过粗；每次请求加载用户的全部项目角色；本地密码登录缺少失败锁定等防护；刷新令牌轮换非原子；服务账号没有项目级授权。

目标部署形态是单租户、多用户、多项目隔离。项目成员关系是常规项目内容访问边界。平台超级管理员负责项目生命周期和管理员治理，但不会自动获得项目内容访问权。

## 目标与非目标

**目标：**

- 将服务端默认租户作为唯一租户范围，客户端不能选择租户。
- 建立安全的本地密码创建、登录、重置、锁定和会话生命周期。
- 分离平台用户治理、项目成员治理和项目内容访问。
- 为超级管理员提供显式项目治理和恢复操作。
- 人类用户和机器身份都只按当前项目范围进行授权。
- 所有治理变更都留下可追责且不包含秘密信息的审计证据。
- 可预测地迁移现有用户、项目、成员关系和活动会话。

**非目标：**

- 多租户 UI 或租户成员模型。
- OIDC、SSO、MFA、邮件邀请或邮件找回密码。
- 通用策略 DSL、ABAC、自定义角色或自动过期的接管授权。
- 超级管理员隐式访问项目业务数据。

## 技术决策

### 1. 保留一个由服务端持有的租户

后端必须在内部解析现有默认租户。传入的 `x-tenant-id` 不得决定授权或审计归属。保留现有 `tenant_id` 字段，因为项目及相关记录已经使用该字段，也能为未来迁移保留清晰边界。

不采用删除租户字段的方案，因为这会产生没有业务收益的破坏性数据库变更。当前产品只有一个组织边界，因此也不实现完整租户成员体系。

### 2. 分离平台项目治理与项目内容授权

新增全局项目清单、项目创建、生命周期管理、管理员恢复和项目接管等平台权限。这些操作只治理项目元数据和成员关系。现有 `project.*` 内容权限继续要求显式项目成员关系。

接管是独立用例：超级管理员必须填写非空原因，随后被显式新增或提升为 `project_admin`，之后再按普通项目角色访问内容。第一版不自动让接管成员关系过期。

不采用把 `platform_super_admin` 隐式当作所有项目 `project_admin` 的方案，因为这会违反现有权限标准并使项目内容隔离失去意义。

### 3. 拆分用户权限，但保留固定角色集合

将粗粒度写权限拆为用户创建、资料修改、状态修改、凭据重置、平台角色分配和超级管理员管理。继续使用现有固定平台角色，不增加自定义角色存储。

初始映射：

- `platform_super_admin`：拥有全部用户治理权限。
- `platform_operator`：可读取用户、创建无平台角色用户，以及修改、启用和停用非超级管理员。
- `platform_viewer`：只能读取用户。
- 第一版中，平台角色分配和凭据重置仅允许超级管理员执行。

最后一个活动超级管理员继续受到保护。操作员不能修改现有超级管理员，也不能授予平台角色。

不实现通用角色编辑器，现有三个固定角色加显式权限已足够覆盖当前需求。

### 4. 管理本地密码与会话安全状态

用户增加连续失败次数和 `locked_until`。管理员创建或重置的密码可直接用于正常登录，不要求用户首次登录时修改；创建和重置流程均写入 `must_change_password=false`。连续五次密码错误后锁定十五分钟；成功登录后清空失败状态。

用户可在安全设置中主动修改密码。修改成功后撤销既有刷新令牌 family 并签发替代会话；管理员重置密码也继续撤销该用户的全部刷新令牌 family。密码强度校验不因取消强制改密而降低。

保留数据库中的 `must_change_password` 字段以兼容已经落地的增量结构，但该字段不再限制登录、刷新、普通 API 或前端路由。已有 `must_change_password=true` 的用户也立即按普通活动用户处理，避免额外数据迁移；字段清理不在本变更范围内。

### 5. 原子轮换刷新令牌并使用标准 JWT 校验

刷新令牌记录增加 family 标识和原子消费状态。轮换通过行锁或条件更新保证同一个令牌只能成功一次。再次使用已消费令牌时撤销整个 family。

统一使用现有 PyJWT 依赖进行编码与解码。令牌必须校验签名、允许算法、签发方、受众、类型、过期时间、生效时间、主体、JWT ID 和签名密钥标识。`kid` 从配置的验证密钥集合中选取密钥；一个密钥负责当前签名，旧密钥在轮换窗口内只负责验证。

不继续扩展自定义解码器，因为现有 JWT 库已经正确实现标准声明和算法校验。

### 6. 只解析当前项目的授权

项目范围从规范路由或 operation 契约解析。只有既有 gateway 契约确实需要时才允许请求头选择项目；请求头永远不能作为成员关系证明，并且目标资源所属项目必须与当前项目一致。

认证请求最多只加载当前项目的角色或 grant。`GET /api/projects/{project_id}/access` 返回当前主体在该项目中的角色和派生权限，供前端工作区使用。登录和个人资料响应不再返回完整项目角色映射，项目列表继续作为用户可见项目的数据源。

不把全部项目成员关系写进 access token，否则撤权和大规模成员关系失效仍然不安全且成本高。

### 7. 增加最小化的服务账号项目授权

新增唯一的 `(service_account_id, project_id)` grant，并复用一个现有 `ProjectRole`。第一版仅超级管理员可以管理这些 grant。API key 认证只识别服务账号身份，随后按当前项目加载活动 grant。账号被停用、令牌撤销或过期、项目被删除、grant 不存在时均拒绝访问。

不实现通用 scope 表达式或 ABAC 引擎；单张 grant 表即可匹配现有项目 RBAC，代码更少且审计更清晰。

### 8. 增加项目范围成员候选人查询

项目管理员通过分页接口查询可加入项目的活动用户，接口只返回选择成员所需的最小身份信息。接口要求 `project.member.write`，但不授予 `platform.user.read`。现有全局用户接口仍只用于平台治理。

### 9. 明确定义治理审计动作

HTTP 审计解析增加用户创建、状态和资料修改、凭据重置、平台角色分配、项目生命周期、管理员恢复、接管、项目成员变化和服务账号项目授权等语义动作。接管原因作为非秘密 metadata 保存。密码、API key、刷新令牌和 Authorization 请求头不得写入审计。

### 10. 使用显式的增量数据库迁移

以仓库现有 Alembic 配置作为用户、令牌字段和服务账号项目授权表的正式迁移路径。现有用户回填 `must_change_password=false`、失败次数为零且无锁定时间。现有刷新令牌在安全可行时回填稳定 family；如无法安全回填并必须使会话失效，实施前必须明确记录。

数据库回滚必须非破坏性：应用回滚后可以停止使用新增列和表，但 downgrade 不得自动删除凭据或授权历史。

## 风险与权衡

- [既有 API 消费端依赖完整 `project_roles`] → 在同一发布中更新 `platform-web`，记录破坏性响应变更，并确认不存在其他正式消费端。
- [账号锁定可被用于拒绝服务] → 锁定仅持续十五分钟，公开响应保持统一，审计失败但不暴露账号是否存在；IP 或网关限流仍由部署层负责。
- [超级管理员接管会提升权限] → 使用独立接口、非空原因、超级管理员权限和语义化审计，不使用隐藏的角色继承。
- [SQLite 与 PostgreSQL 的并发刷新行为不同] → 使用两者均可测试的条件状态迁移，在支持时使用行锁。
- [引入 Alembic 会暴露既有迁移债务] → 本变更只提交增量且范围明确的 revision，不顺手清理无关数据库问题。
- [切换项目时需要额外授权请求] → 只在前端工作区缓存当前项目授权，成员关系改变后刷新；暂不增加分布式权限缓存。

## 迁移计划

1. 增加增量数据库结构并回填安全默认值。
2. 部署后端的新权限、当前项目授权查询、密码状态、令牌 family 轮换、服务账号 grant 和审计动作；在实际可行时保留读取兼容。
3. 更新 `platform-web` service、权限类型、工作区授权加载、用户流程、项目治理、成员候选人和服务账号授权页面。
4. 正式前端不再依赖完整项目角色映射后，从登录和个人资料响应中移除该字段。
5. 发布前完成本地测试、最短 API/UI 链路验证、迁移升级验证和 owner 验收。

回滚方式：回滚应用行为但保留新增数据库结构。若响应契约已切换，前端和 API 必须一起回滚。不得恢复已经消费的刷新令牌，也不得暴露任何已存秘密信息。
